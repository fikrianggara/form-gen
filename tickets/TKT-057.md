## Description

Key-reading visibility by org role: a user whose org role is **org-dev** can
read the API keys belonging to their organization AND their own keys; a
plain (global) dev with no org membership can only read their own keys.
Builds on the org-membership model (TKT-055), org role changes (TKT-056), and
the org-binding of keys (TKT-039, currently backlog: `organizationId` on
ApiKey/ApiKeyRequest).

Owner request (2026-08-21): "kalo user rolenya dev organisasi, maka dia bisa
baca key yang ada di organisasi dan key dia. ketika hanya dev biasa, maka dia
cuma bisa baca punya dia aja."

## Acceptance criteria

- [ ] TKT-039 lands first or in the same wave: ApiKey.organizationId +
      ApiKeyRequest.organizationId (org-aware v1 route filters).
- [ ] `listApiKeys` becomes visibility-aware: ADMIN sees all; org-dev sees
      keys where `organizationId == session org` OR `createdBy == session
      sub`; plain DEV sees only `createdBy == session sub`; OPERATOR sees
      none unless they have issued keys.
- [ ] The API-keys admin panel (`getAdminApiKeyDashboard`) filters rows by the
      same rule; a non-org dev cannot see org keys.
- [ ] Key issue: an org-dev issuing a key may bind it to their org; a plain
      dev may not.
- [ ] Removing a member from an org (TKT-056) immediately removes their
      org-key visibility (membership re-check per read, not cached).
- [ ] Integration tests: org-dev sees org+own keys, plain dev sees own only,
      operator sees none, member removal revokes org visibility.

## Notes

- Sequencing: strictly after TKT-055 (+ TKT-039). Grouped separately so the

- v1 route filters for org-scoped access are TKT-039's concern; this ticket

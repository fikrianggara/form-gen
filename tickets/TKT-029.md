## Description

Disabling a user blocks NEW logins (`authenticate` rejects `!isActive`) but
does NOT terminate an EXISTING session: the middleware only verifies the JWT
signature/expiry and never checks `isActive`, so a disabled user keeps working
until the 7-day cookie expires. "Disable" should mean "cannot use the system",
not merely "cannot log in again". Also add a self-lockout guard: an ADMIN can
currently disable their own account or the last active ADMIN.

## Acceptance criteria

- [ ] Session verification checks `isActive` for the session's user on
      protected routes (/dashboard*, /admin*); disabled user's existing
      session is rejected on the next request
- [ ] Middleware or a small session-verification helper performs the check;
      one indexed primary-key lookup per protected request
- [ ] Admin cannot disable their OWN currently-logged-in account
- [ ] Admin cannot disable the LAST active ADMIN (at least one active ADMIN
      must remain)
- [ ] Login behavior unchanged: inactive users still get the generic
      invalid-credentials response (no account-state leak)
- [ ] Unit + integration tests green (session rejection, self-lockout, last-
      admin guard)

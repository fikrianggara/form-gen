## Description

`Invitation.responseId` is a plain `String?` with no FK — the schema allows
dangling refs and the detach is manual in `deleteResponse`
(`src/services/response-admin.service.ts`). From finding F-009.

## Acceptance criteria

- [x] Migration: `Invitation.responseId` becomes a proper relation to
      `Response` (nullable, onDelete semantics decided — e.g. SetNull)
      (schema: `response Response? @relation(fields:[responseId],
      references:[id], onDelete: SetNull)` + `@@index([responseId])`;
      migration 20260815170000_invitation_response_fk adds the FK with
      ON DELETE SET NULL — verified on a scratch DB: deleting a response
      detaches its invitation)
- [x] `deleteResponse` no longer needs the manual detach (cascade handles it),
      or the manual detach stays as defense-in-depth and is verified
      (manual updateMany detach kept as defense-in-depth; the FK is the real
      guarantee — a test bypasses the service and deletes the response
      directly, proving the constraint detaches invitations)
- [x] Existing invitations migrate cleanly (no data loss)
      (nullable FK, no data rewrite; dev DB has no dangling refs; migration
      applied to all three ticket DBs + dev DB)
- [x] Tests cover delete-response → invitation detach
      (response-admin.service.test.ts: deleteResponse detaches a linked
      invitation; direct db.response.delete also detaches via the FK)

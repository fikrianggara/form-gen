## Description

Add the organizational dimension to public API access (analysis v04): an API
key is either global (admin-issued) or bound to one organization; every v1
route filters data by the key's org so one org's consumer cannot read
another org's questionnaires, responses, or reports. Without this, an
org-bound key leaks PII across orgs.

DEPENDS on TKT-014 (org scoping) being merged to main first — the
Organization/Survey models must exist in main's schema.

## Acceptance criteria

- [ ] `ApiKey.organizationId String?` (FK, SetNull) — null = global key, non-null = org-bound; migration applied
- [ ] `ApiKeyRequest.organizationId String?` replaces/augments the free-text organization field; validated against real orgs
- [ ] Key-based org gate in `withApiKey`/`api-key.service` (parallel to `assertCanManageQuestionnaire`): global keys pass all; org-bound keys restricted to their org
- [ ] questionnaires list/detail: org-bound key sees only questionnaires whose survey belongs to its org; legacy `surveyId=null` visible to global keys only (decision noted in v04 §3.3)
- [ ] responses list/detail + report: inherit the questionnaire's org gate — foreign org returns 403/404, not data
- [ ] masters:read: reuse `listQuestionMasters` semantics — public (`isPublic=true`) + legacy (`organizationId=null`) + own org; cross-org public masters remain visible (dashboard parity)
- [ ] option-sets:read: stays global (model has no org dimension); documented in the API guide
- [ ] Admin UI (TKT-036) + portal approval (TKT-035) gain an org selector when issuing/approving keys
- [ ] Tests: cross-org isolation — key for org A cannot read org B's questionnaire/response/report (403/404); global key can read all; masters public-visibility respected

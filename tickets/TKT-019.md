## Description

Invitation emails currently embed a RELATIVE link
(`/f/<slug>?invite=<token>` — `src/services/invitation.service.ts`,
`src/services/response-admin.service.ts`). Once real mail delivery lands
(TKT-020/013), recipients click a relative path that resolves against their
mail client, not the app. Add an absolute base URL configuration and build
links from it. From finding F-002.

## Acceptance criteria

- [x] New env config for the app's public base URL (e.g. `APP_URL` /
      `NEXT_PUBLIC_APP_URL`), documented in `.env.example`
      (`APP_URL` added to `.env.example` with explanation; read by
      `getAppBaseUrl()` in src/services/invitation.service.ts)
- [x] `sendInvitations` and `mailblastRespondent` build
      `<base>/f/<slug>?invite=<token>` absolute links
      (new `buildInvitationLink()` in invitation.service.ts, wired into both
      call sites; browser-verified: mail log shows
      `https://forms.example.com/f/customer-feedback?invite=…` with
      APP_URL set)
- [x] Missing/invalid base URL handled gracefully (config error surfaced, not
      silently broken links)
      (missing → relative link (dev/console fallback works); invalid/non-http(s)
      APP_URL → AppError `INVALID_APP_URL` thrown with a clear message)
- [x] Tests cover the link builder with and without base URL
      (tests/unit/invitation-link.test.ts: relative, absolute, trailing-slash
      normalization, explicit override, invalid URL + non-http(s) throw;
      integration tests assert absolute links in sendInvitations and
      mailblastRespondent when APP_URL is set)

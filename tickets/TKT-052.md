## Description

Surface newly registered (inactive) users to admins so activation is a
one-click action. The mechanism exists (`setUserActive`, the Enable/Disable
kebab action from TKT-028, and `isActive` checked at login from TKT-029), but
there is no way for an admin to *see* who is pending activation.

Owner request (2026-08-21): "user bikin akun… nanti admin yang aktivasi user."

## Acceptance criteria

- [ ] Users panel shows an explicit "Pending activation" badge/filter for
      `isActive = false` accounts (reuse the pure status-badge pattern from
      TKT-028 — badges are display-only).
- [ ] Kebab menu on a pending user shows "Activate" as a labeled action (not a
      hidden badge toggle); clicking it calls `setUserActive(id, true)` and
      the row updates without a full page reload (R1 convention from
      analysis v06).
- [ ] A deactivated user (admin-disabled, TKT-029) is visually distinct from
      a pending-activation user, or the same badge works for both — decision
      noted in the ticket.
- [ ] No self-lockout regression: activating yourself is impossible only
      because you are already active; the TKT-029 guards stay intact.
- [ ] Component test (Testing Library) for the Activate action mirroring
      TKT-044's pattern.

## Notes

- Pairs with TKT-051 (public signup). Small because it reuses the existing
  kebab/status machinery — the gap is discoverability, not capability.
- Consider an optional "N pending" indicator on the Admin link when inactive
  users exist.

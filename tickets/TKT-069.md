## Description

A daily AI credit system. Every user gets a daily allowance (global default
**20** credits, admin-configurable); the balance resets daily. Spending:
**5** credits to generate a questionnaire from a prompt (regardless of how
many questions it produces), **2** to add a question with AI, **1** to edit a
question with AI. Verified: no credit mechanism exists anywhere in the
codebase today; the only AI spend surface is
`generateQuestionnaireAction` (`src/lib/actions/dashboard.ts:602`) calling
`rag.service:generateQuestionnaireFromPrompt` (rag.service.ts:80), which is
currently free.

Owner request (2026-08-21): "tambah sistem kredit AI, direset harian. 20
kredit per hari, ngabisin 5 buat generate kuesioner (dah termasuk generate
berapapun pertanyaannya), 2 buat pertanyaan, 1 buat edit pertanyaan."
Owner decisions (2026-08-21, analysis v09): proposal-approval generation
(TKT-061) charges the **proposer**; "set kredit user" = per-user allowance
override AND a dated balance adjustment.

## Acceptance criteria

- [ ] Schema (migration):
      - `AiCreditConfig` single row: `dailyDefault Int @default(20)`.
      - `User.aiCreditsPerDay Int?` — per-user daily allowance override.
      - `AiCreditUsage` (userId, date, used Int; `@@unique([userId, date])`).
      - `AiCreditAdjustment` (userId, date, delta Int, reason String,
        createdBy String?, createdAt) for dated balance top-ups/revokes.
- [ ] Daily reset is **inherent** (date-keyed usage, no cron): balance(today)
      = allowance(user) − used(user, today) + Σ adjustments(user, today),
      where allowance = `aiCreditsPerDay ?? config.dailyDefault`.
- [ ] `credit.service.ts` exposes `availableCredits(userId)`,
      `deductCredits(userId, cost, reason)` (atomic: transaction upserting
      the usage row with a conditional `used + cost <= allowance + adj`
      update; throws a typed INSUFFICIENT_CREDITS error when it fails),
      `refundCredits(userId, cost, reason)`.
- [ ] `generateQuestionnaireAction` deducts **5** BEFORE calling the RAG
      pipeline; if the generation throws, the deduction is refunded — a
      failed generation must never cost credits, a successful one always
      deducts exactly 5.
- [ ] Cost schedule enforced via the shared service (not hardcoded per call):
      5 questionnaire · 2 add question · 1 edit question; add/edit wiring is
      TKT-062's hook.
- [ ] Insufficient credits → typed error surfaced in the UI: "AI credits
      exhausted — remaining 0, resets tomorrow" (no partial work, no
      questionnaire created).
- [ ] Visible balance on the Generate page (`GenerateForm`) showing today's
      remaining credits; shell top bar shows it once TKT-058/TKT-069 merge
      (cross-ref in TKT-058).
- [ ] Race-safe: two concurrent generations cannot both succeed on 19 credits
      (transactional deduction).
- [ ] Integration tests: deduct-5 success; insufficient blocked; refund on
      LLM failure; next-day reset restores the full allowance; per-user
      override honored; adjustments affect the balance.

## Notes

- Timezone for the daily boundary: server local (WIB) — note as an
  assumption; flip to UTC if the owner wants a fixed boundary.
- Rate limit + credit check both gate generation; order: permission →
  credits → LLM call.
- The proposal-approval flow (TKT-061) charges the proposer via this service;
  its retry action is the deduction point.

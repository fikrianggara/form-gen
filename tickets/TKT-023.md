## Description

Public response endpoints (`POST /api/questionnaires/[slug]/responses`,
`PATCH .../responses/[id]`) are unthrottled — anonymous bots can spam Response
rows and payloads (storage/CPU DoS) on any ACTIVE questionnaire. The
`rate-limit.service.ts` exists but is wired only to the dashboard login.
From finding F-004.

## Acceptance criteria

- [x] Rate limiting on POST/PATCH response routes per (respondentToken/IP) —
      `assertResponseSubmissionAllowed` checks three windowed keys before any
      write: `submit:<token>:<ip>` (60/min), `submit:ip:<ip>` (120/min, catches
      token-minting bots), and `submit:q:<questionnaireId>` (10 000/hour).
- [x] Configurable window/limit; documented constants — `RESPONSE_WINDOW_MS`,
      `RESPONSE_MAX_PER_TOKEN_IP`, `RESPONSE_MAX_PER_IP`, `RESPONSE_Q_WINDOW_MS`,
      `RESPONSE_MAX_PER_QUESTIONNAIRE` in `src/services/rate-limit.service.ts`
      with doc comments.
- [x] 429 with stable error shape when the limit is hit — shared `RATE_LIMITED`
      AppError (status 429, code `RATE_LIMITED`, message "Too many requests...").
- [x] Rate-limit service generalized/reused beyond login — generic
      `assertWithinLimit`/`recordRateLimitEvent` over the new `RateLimitEvent`
      table; login flow unchanged (LoginAttempt table, same semantics) and all
      existing login rate-limit tests stay green.
- [x] Tests cover under/over limit and window expiry — 8 new integration tests
      in `tests/integration/rate-limit.service.test.ts` (under limit, over
      limit 429, per-respondent scoping, IP cap, questionnaire cap, window
      expiry, recorded keys, next-hour window).

## Description

Owner decision (2026-08-19): the self-serve portal (TKT-035) and admin panel
(TKT-036) exist, but API-key issuance is ADMIN-only. Operators should be able
to issue keys, or a new DEV role should combine operator abilities with key
issuance. Decision: **new DEV role** = OPERATOR permissions + direct API-key
issuance/revocation. Approving external portal requests stays ADMIN-only
(trust boundary). Requires splitting the coarse `MANAGE_API_KEYS` permission
into granular ones.

## Acceptance criteria

- [ ] Prisma `Role` enum gains `DEV`; migration applied to ticket + dev DB
- [ ] New permission `ISSUE_API_KEYS`; DEV gets OPERATOR perms + `ISSUE_API_KEYS`; ADMIN retains full `MANAGE_API_KEYS` (approve/deny portal) + `ISSUE_API_KEYS`
- [ ] `issueApiKeyAction` + `revokeApiKeyAction` require `ISSUE_API_KEYS`; `approveApiKeyRequestAction`/`denyApiKeyRequestAction` require `MANAGE_API_KEYS`
- [ ] UsersPanel role dropdown + user-create form offer DEV; DEV user can access /admin/api-keys
- [ ] Admin api-keys page: DEV sees key list + issue + revoke; approval queue section hidden for DEV (admin-only)
- [ ] RBAC unit tests cover DEV matrix; integration test proves an OPERATOR still cannot issue keys
- [ ] `npx tsc --noEmit` passes; lint + build green

## Notes

Split: keep `MANAGE_API_KEYS` (admin-only, portal approval) and add
`ISSUE_API_KEYS` (admin + dev, direct issue/revoke). Analysis: see register
v03 §3.3 + owner decision recorded 2026-08-19.

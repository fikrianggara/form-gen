## Description

A logged-in **operator** can request an API key from inside the app. When an
admin approves that request, the key is created AND the user is automatically
promoted to role `DEV` — no separate "apply to be dev" step. Today
`ApiKeyRequest` is an anonymous external portal
(`src/services/api-key.service.ts:createApiKeyRequest`); the approval flow
exists but is not linked to a requesting user and does not touch roles.

Owner request (2026-08-21): "operator bisa mengajukan api key, ketika admin
approve pengajuan key, maka user otomatis jadi dev."

## Acceptance criteria

- [ ] Schema: `ApiKeyRequest.requesterUserId String?` + relation to User
      (migration; existing portal rows keep null).
- [ ] Logged-in operator sees a "Request API key" form (name, scopes, purpose)
      in the API keys area; submission creates a PENDING request linked to
      their user id.
- [ ] Admin approval of a user-linked request: creates the key (existing
      `approveApiKeyRequest`) AND promotes the requester's role to DEV when
      they are currently OPERATOR (never demotes; admins/devs unchanged).
- [ ] Admin denial leaves the operator's role unchanged.
- [ ] Once promoted, the user has `ISSUE_API_KEYS` and can issue/revoke keys
      (permission map `src/lib/auth/rbac.ts` picks this up automatically).
- [ ] The anonymous portal flow (TKT-032) keeps working unchanged.
- [ ] UI: admin approval panel shows the linked user's name/email; operator
      sees request status (pending/approved/denied) and the one-time secret
      when approved.
- [ ] Integration test: operator requests → admin approves → role becomes DEV
      and a new key exists owned by the promotion.

## Notes

- Guard: promotion must only happen for OPERATOR→DEV; never downgrade, never
  promote a disabled user.
- The requested scopes must respect the future org-key model (TKT-057) —
  keep `organizationId` off this ticket, it belongs to TKT-039.

## Description

Sign in with Google. A brand-new Google account registers automatically as an
**active** `OPERATOR` (skipping the admin-activation step from TKT-051); an
existing account whose email matches is linked and signs in. Password-based
login stays available.

Owner request (2026-08-21): "nanti bisa pake google auth, otomatis jadi aktif
usernya dengan role operator."

## Acceptance criteria

- [ ] "Continue with Google" button on the login (and register) page starts
      the OAuth flow; callback exchanges the code for the profile.
- [ ] First-time Google sign-in with an email not in `User` creates a user
      with `isActive = true`, `role = OPERATOR`, `name` from the Google
      profile, and a non-login placeholder `passwordHash` (unusable bcrypt
      value — Google users never log in with a password).
- [ ] Returning Google sign-in matches by email, signs in the existing user,
      and does NOT change their role or isActive state.
- [ ] Inactive existing user signing in via Google is rejected (activation
      policy still applies — Google auto-active only for NEW accounts).
- [ ] Session cookie + `signSession` reused unchanged; logout works.
- [ ] Env vars documented (Google client id/secret); local dev callback URL
      configured; integration test with a mocked Google token endpoint.

## Notes

- Scope: decide OAuth2 code flow vs NextAuth (project has no auth library
  today — hand-rolled session in `src/lib/auth/session.ts`). A custom
  OIDC route pair (`/api/auth/google/start`, `/api/auth/google/callback`)
  keeps the dependency surface small; NextAuth adds a library but less
  plumbing. Trade-off documented in analysis v07 Q2.
- P2 by owner's "nanti" phrasing — not part of the current activation wave,
  but the schema must not block it (email is already unique).

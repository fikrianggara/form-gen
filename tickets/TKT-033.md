## Description

Service layer for the public REST API keys (analysis v03 §6/§8): SHA-256
hashing, key lifecycle (issue/rotate/revoke/list), scope enforcement, and a
`withApiKey` route wrapper that composes auth + scope + rate-limit + logging.

## Acceptance criteria

- [x] Keys generated as high-entropy secrets (e.g. 32+ random bytes, `fg_live_` prefix); only keyHash (SHA-256) and keyPrefix stored; plaintext shown exactly once at creation
- [x] `issueApiKey` (name, scopes, expiresAt?) creates an ACTIVE key; `rotateApiKey` issues a new secret and revokes the old; `revokeApiKey` flips status; `listApiKeys` returns metadata incl. prefix, scopes, status, lastUsedAt — never the secret
- [x] `requireApiKey(request)` validates Bearer key: exists, ACTIVE, not expired; updates lastUsedAt; throws UNAUTHORIZED (401) otherwise
- [x] `requireScope(scope)` rejects valid keys lacking the scope with SCOPE_FORBIDDEN (403)
- [x] `withApiKey(handler, scopes)` wrapper: auth → scope → per-key rate limit (`assertWithinLimit`) → handler; every v1 route uses it
- [x] Request logging writes metadata (key id, method, path, status, durationMs, ip, user-agent) to ApiRequestLog — never bodies
- [x] Unit tests cover: hash round-trip, issue/rotate/revoke, expiry check, missing/invalid/revoked key → 401, missing scope → 403, rate limit → 429

## Notes

Reuses existing `rate-limit.service.ts` (`assertWithinLimit`/`recordRateLimitEvent`) — do NOT build a second rate-limit system.

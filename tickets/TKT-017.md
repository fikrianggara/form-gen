## Acceptance criteria

- [x] Questionnaire records its creator (createdBy); ADMIN can manage any questionnaire's responses, OPERATOR only their own (legacy unowned questionnaires stay manageable by any admin/operator)
- [x] Responses list shows a per-row action button that opens a popup menu with View / Edit / Delete / Mailblast
- [x] View opens the existing response detail page
- [x] Edit opens the response prefilled and saves updates to answers (reusing the save engine)
- [x] Delete removes the response (and its answers) after confirmation
- [x] Mailblast sends the questionnaire's unique link to the respondent's email (reusing invitation + mail services); no response rows created by the blast itself
- [x] Actions are permission-gated server-side (not just hidden in UI)
- [x] Unit + integration tests green

### Verification (audit 2026-08-15)

- [x] `Questionnaire.createdBy` (nullable FK, migration `20260815110000_questionnaire_creator`); `assertCanManageQuestionnaire` in `src/services/access-control.service.ts` (admin any / operator own-or-null / else Forbidden).
- [x] `ResponseActionsMenu` (kebab popup: View link, Edit link, Mailblast, Delete with inline confirm) wired into the responses list page.
- [x] View → existing `/responses/[rid]` detail page.
- [x] Edit → `/responses/[rid]/edit` server page gates via `assertCanManageQuestionnaire`, `ResponseEditForm` prefills from `getResponseDetail` and saves via `updateResponseAction` → `saveResponse`.

- [x] `mailblastRespondent` find-or-creates an invitation for the respondent email and sends the link; no new Response rows.
- [x] All actions call `requirePermission(MANAGE_QUESTIONNAIRES)` + ownership gate server-side.

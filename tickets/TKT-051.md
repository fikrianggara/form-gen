## Description

Anyone can register with **username**/email/password on a public signup page.
The account is created **inactive** (`isActive = false`, role `OPERATOR`) and
cannot log in until an admin activates it. Today users can only be created by
an admin (`src/services/user.service.ts:createUser`); there is no public
signup, and the login page copy says "Admin and operator access only"
(`src/app/login/page.tsx:25`). `authenticate()` already rejects inactive
users (`src/services/user.service.ts:137`), so activation gating login comes
for free once signup writes `isActive: false`.

Owner request (2026-08-21): "user bikin akun dengan username/email dan
password, nanti admin yang aktivasi user."
Owner decision (2026-08-21, analysis v08 Q1): add a **unique username
column** to User; login accepts username OR email.

## Acceptance criteria

- [ ] Schema: `User.username String @unique` (migration; nullable-first with
      backfill of `email` local-part for existing rows, then non-null).
- [ ] Public `/register` page collects username, email, password (min 8 chars,
      validated by `validatePassword`) with client + server validation;
      duplicate username OR email returns the existing conflict error.
- [ ] Login (`loginAction`/`authenticate`) accepts username OR email in the
      email field — normalize lookup to either unique field.
- [ ] New inactive user CANNOT sign in — `authenticate` rejects them with the
      same "Invalid email or password" response as a wrong password.
- [ ] Admin can activate the account via the Users panel (see TKT-052);
      once active, the user signs in normally with username or email.
- [ ] Registration page has a link back to sign in; success message tells the
      user their account awaits admin activation.
- [ ] Unit + integration tests: signup creates inactive user with unique
      username, login rejected before activation, login succeeds after
      activation (by username and by email).

## Notes

- Reuses `createUser`/`validatePassword`/`setUserActive`; only the entry point
  and the `isActive: false` default are new.
- Q1 decided: dedicated `username` column (unique), login by username or
  email; `User.name` remains the display name (TKT-059 homepage header shows
  username, falling back to name).
- Gate the signup endpoint with the existing rate-limit machinery
  (`rate-limit.service`) to prevent registration spam.

## 4. Root-cause taxonomy

**Class A — Frontend/UI defects (3 of 5 = 60%).** All three live in the
`admin-polish` group, which merged 6 features (TKT-011, 016, 018, 028, 029, 031) plus these 3 bugs → a 33% bug rate, the highest of any group. Three
distinct mechanisms:

- **A1 — client state not reconciled after a server action (TKT-015).** The
  action persisted the change but returned nothing usable to the client, so
  the UI required a reload. The happy path was verified; the "does the screen
  reflect it immediately" path was not an acceptance criterion.
- **A2 — React event object touched after an async gap (TKT-027).**
  `e.currentTarget` is nulled once the handler yields; calling `.reset()` after
  `await` crashes. A well-known React pitfall with no lint rule or convention
  guarding it.
- **A3 — CSS containment clips overlays (TKT-030).** A kebab menu inside an
  `overflow-hidden` table wrapper gets cut off. Latent by nature — it only
  manifests when a popup is added inside an existing clip.

**Class B — Security/hardening defects (2 of 5 = 40%).** Both were caught
**proactively by the analysis register** (F-004 unthrottled auth endpoint,
F-010 unescaped mail HTML) — i.e. by audit, before any user or attacker hit
them. This is the register working as designed; the finding→ticket loop
closed in the same day.

**Timing pattern.** All five bugs were filed in a two-day window
(08-14..08-15), which is exactly when the UI-heavy `admin-polish` group and
the `invitation-hardening` group were merged. Bug inflow is not uniform — it
spikes with UI-feature merge waves, not with data/service work.

## 5. Why bugs occur (causal chain)

1. **Acceptance criteria verify persistence, not immediate UI reflection.**
   TKT-015's fix required the action to _return_ the created entity so the
   client could append it — a contract that was never specified, only
   discovered by the user.
2. **No component-level tests exist.** The suite is service-level unit +
   integration tests; interactive panel behavior (state update after submit,
   reset-after-success, popup visibility) is untested. A Testing Library test
   would have caught A2 (reset crash) and A1 (stale list) at build time.
3. **No security checklist gate on feature merge.** F-004 and F-010 were
   found _after_ their features were merged; a pre-merge escape/rate-limit
   check would have prevented two of the five bugs outright.
4. **Frontend conventions are not codified.** `overflow-hidden` + popup,
   `currentTarget` after await, and "action must return what the UI needs"
   are all repeatable traps; none is written in AGENTS.md or enforced by lint.

## 6. Recommendations (in priority order)

| #   | Recommendation                                                                                                                                                                                                                                                                                                       | Kills      | Cost                             |
| --- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ---------- | -------------------------------- |
| R1  | **Add a standard AC line to every data-mutating ticket:** "UI reflects the change immediately without reload (browser-verified)". The `done` gate already refuses unchecked boxes — this makes it mandatory.                                                                                                         | A1         | trivial (doc)                    |
| R2  | **Codify frontend rules in AGENTS.md:** (a) never touch `e.currentTarget` after `await` — capture before the gap; (b) popups/menus must not live under `overflow-hidden` ancestors — use `overflow-visible` or a portal; (c) server actions that mutate return the created/updated entity for client reconciliation. | A2, A3, A1 | trivial (doc)                    |
| R3  | **Add component tests for interactive panels** (Testing Library): editor add/toggle, user-create reset path, kebab menu visibility in a table wrapper. Wire into the gate chain (`vitest` run).                                                                                                                      | A1, A2, A3 | medium (one test file per panel) |
| R4  | **Security checklist at merge time (or in AC):** escape every interpolation into HTML/mail (reuse `escapeHtml`), rate-limit every public/auth endpoint, access-control on every new server action. The register's F-004/F-010 prove the audit catches these — run it before merge, not after.                        | B (both)   | low                              |
| R5  | **Keep the analysis register as the proactive bug net** — it caught 40% of all bugs. Run a short analysis pass after every UI-feature merge wave (the data shows bugs cluster there).                                                                                                                                | B          | low                              |
| R6  | **Optionally: custom ESLint rule** for "member access on `currentTarget` after `await`" — small AST rule; nice-to-have, R2 + R3 cover most of the value first.                                                                                                                                                       | A2         | high for the value               |

Two viable paths overall: **(1) convention+AC approach (R1, R2, R4, R5)** —
near-zero cost, prevents the recurring classes by making them explicit at the
gate; **(2) test-first approach (R3, R6)** — real regression protection but
requires writing component-test infrastructure. Recommendation: do R1+R2+R4
immediately (they are doc-level), then R3 as the next ticket.

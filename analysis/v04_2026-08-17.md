## 1. Question answered

**Does the current analysis (v03) include organizational scope?**

No. v03 models capability scopes only (`questionnaires:read`,
`responses:read`, `reports:read`, `masters:read`, `option-sets:read`) and the
proposed `ApiKey` model has no organization dimension. Nothing in v03 ties an
API key to an organization or filters v1 responses by org.

Additionally, the org-scoping code itself (TKT-014) is **not yet on main** —
it sits on `feature-TKT-014-organization-scoping-org` (done/readyToMerge).
v03 was therefore grounded on the pre-org schema; the two features must be
reconciled at implementation time.

## 3. Impact on the public REST API (TKT-032..038)

### 3.1 ApiKey model (TKT-032) — schema change required

The proposed `ApiKey` has no `organizationId`. Without it, an API key issued
to one org's consumer could read every org's questionnaires, responses, and
reports — a **cross-org data leak** (responses contain PII). Required:

```prisma
organizationId String?  // null = global key (admin-issued); non-null = org-bound
organization   Organization? @relation(fields: [organizationId], references: [id], onDelete: SetNull)
```

This mirrors the existing `User.organizationId` convention. The scope list
stays capability-only; **org becomes a second axis** on the key (action +
resource, AWS-IAM style), not a scope string.

### 3.2 Portal request (TKT-035) — org must be real

`ApiKeyRequest` already carries `organization String?` as free text. For org
scoping it should become `organizationId String?` validated against real
organizations at approval time (admin picks the org; requester can suggest
by name/email). Approval flow: admin binds the issued key to an org.

### 3.3 v1 route filters (TKT-034) — per-endpoint org semantics

| Endpoint                      | Org behavior                                                                                                                                                           |
| ----------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| questionnaires list/detail    | key.organizationId bound: only questionnaires whose survey belongs to that org (legacy `surveyId=null` decision needed — recommend visible to global keys only)        |
| responses list/detail, report | inherit the questionnaire's org gate (403/404 for foreign org)                                                                                                         |
| masters:read                  | reuse `listQuestionMasters` semantics: public (`isPublic=true`) + legacy (`organizationId=null`) + own org — cross-org public masters stay visible, matching dashboard |
| option-sets:read              | **no org dimension** in the model — stays global; document this in the API guide                                                                                       |

### 3.4 API-key org gate (TKT-033) — parallel to session gate

`access-control.service.ts` gates are session-based. The API needs an
equivalent key-based check (`assertApiKeyOrgAccess(key, organizationId)` or
fold into `withApiKey`): global keys pass everything; org-bound keys pass
only their org. Reuse the same semantics; do not fork the service.

## 4. Impact on other features (not just the API)

1. **Dashboard questionnaire list — gap in TKT-014 itself.** On the TKT-014
   branch, `dashboard/page.tsx:17` calls `listQuestionnaires()` which has NO
   org filter. An OPERATOR in org A sees org B's questionnaires in the list
   (management actions are gated, but the list leaks). Recommend a small
   follow-up: org-filter `listQuestionnaires` for non-ADMIN (matching
   `listSurveys`/`listQuestionMasters` behavior). Related to, but separable
   from, the API ticket.
2. **Respondent flow (`/f/[slug]`)** — org-agnostic by design; public forms
   must stay reachable regardless of org. Org scoping must NOT leak into the
   respondent submission path.
3. **Reports** — report generation is per-questionnaire; org gate applies
   through the questionnaire, no report-specific change.
4. **Rate limiting / request logging** — org-agnostic (per-key); no change.
5. **Sequencing** — TKT-014 must merge before the org-scoped API work can
   land (Organization/Survey must exist in main's schema). The seven API
   tickets (TKT-032..038) proceed as filed; this org ticket builds on top.

## 5. Recommendation

File one backlog ticket (P1, medium, group `public-api`):

- Add `organizationId` to `ApiKey` (+ migration) and `ApiKeyRequest`.
- Add key-based org gate in `withApiKey` / `api-key.service`.
- Org-filter v1 routes: questionnaires/responses/report by key org;
  masters by `listQuestionMasters` semantics; option-sets global.
- Admin UI (TKT-036) gains an org selector when issuing/approving keys.
- Tests: cross-org isolation (key A must not read org B data — 403/404).

Optional follow-up (separate, small): org-filter the dashboard
questionnaire list (TKT-014 gap noted in §4.1).

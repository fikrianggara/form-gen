## 3. Impact analysis

### 3.1 Schema change is mandatory (M2M)

`Questionnaire.surveyId String?` (single FK) cannot express "one
questionnaire in many surveys". Required:

```prisma
model SurveyQuestionnaire {
  surveyId        String
  survey          Survey        @relation(fields: [surveyId], references: [id], onDelete: Cascade)
  questionnaireId String
  questionnaire   Questionnaire @relation(fields: [questionnaireId], references: [id], onDelete: Cascade)
  createdAt       DateTime      @default(now())
  @@id([surveyId, questionnaireId])
  @@index([questionnaireId])
}
```

- `Questionnaire.surveyId` is **dropped**; `Survey.questionnaires` and
  `Questionnaire.surveys` become implicit M2M via the join table.
- Data migration: existing `questionnaire.surveyId` rows → join rows
  (backfill), then drop the column.
- This is a breaking schema change — affects access-control, editor,
  org page counts, API scoping (see below).

### 3.2 Access-control must change

`assertCanManageQuestionnaire` currently checks
`q.survey.organizationId === session.organizationId` (single survey).
Under M2M the org gate becomes: **any of the questionnaire's surveys belongs
to the caller's org** (or creator/legacy rules unchanged):

```
q.surveys.some((s) => s.organizationId === session.organizationId)
```

Edge case to decide: may a questionnaire be linked to surveys in DIFFERENT
organizations? Recommend: yes at the data layer (a shared questionnaire
across orgs is legitimate, e.g. BPS reuse), but then org access is a UNION
over its surveys' orgs. For the questionnaire EDIT page, the survey
selector becomes multi-select.

### 3.3 API scoping interaction (TKT-039)

TKT-039's org filter ("questionnaires list → only those whose survey belongs
to the key's org") must be updated for M2M: a questionnaire is visible to an
org key if **ANY of its surveys** belongs to that org. Same for responses /
report (they inherit the questionnaire). Note this dependency in TKT-039 —
do NOT implement TKT-039 against the single-FK assumption; the schema must
land first (or be reconciled at implementation).

### 3.4 Delete survey semantics

With the join table onDelete: Cascade, deleting a survey:
- removes the survey + its join rows;
- **keeps the questionnaires** (they just lose that survey link) — this
  matches "detach, don't destroy" and is safe for questionnaires shared
  across surveys;
- must respect org gates: ADMIN any; OPERATOR only own org's surveys
  (reuse `assertCanAccessSurvey`).

Delete entry points: survey page (per requirement) + org page survey row
(kebab menu, matching the ResponseActionsMenu / UsersTable convention:
explicit labeled actions + inline confirm).

### 3.5 Other touches

- `listQuestionnaires` + dashboard cards: include `surveys` for tags.
